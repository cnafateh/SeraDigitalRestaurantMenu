# عملیات، انتشار و عیب‌یابی

## دو روش اجرای Compose

| فایل                      | منبع برنامه                                                 | اتصال شبکه                         | دسترسی مرورگر                                         |
| ------------------------- | ----------------------------------------------------------- | ---------------------------------- | ----------------------------------------------------- |
| `docker-compose.yml`      | build از `Dockerfile` مخزن                                  | `DB_NETWORK` خارجی                 | پورت میزبان `${SERA_PORT:-3000}` → پورت 80 کانتینر    |
| `docker-compose.prod.yml` | pull از `ghcr.io/cnafateh/seradigitalrestaurantmenu:latest` | `DB_NETWORK` و `NPM_NETWORK` خارجی | alias `sera-menu:80` از reverse proxy؛ بدون host port |

هر فایل فقط یک سرویس به نام `app` دارد. هیچ سرویس PostgreSQL یا Nginx در Compose فعلی تعریف نشده است. دو فایل را هم‌زمان به‌عنوان دو استقرار مستقل روی یک دیتابیس اجرا نکنید مگر این‌که واقعاً دو نمونهٔ برنامه می‌خواهید. هر دو نمونه به همان جدول‌ها و volumeهای تعریف‌شده در پروژهٔ Compose خود متصل می‌شوند.

## انتشار ایمیج در GitHub Actions

workflow [`.github/workflows/docker-publish.yml`](../.github/workflows/docker-publish.yml) روی push به `main`، tagهای `v*`، pull request به `main` و اجرای دستی فعال می‌شود. برای pull request ایمیج فقط ساخته می‌شود و push نمی‌شود. برای push مجاز، workflow با Buildx ایمیج `linux/amd64` را در GHCR منتشر می‌کند. tagهای workflow شامل `latest` برای شاخهٔ پیش‌فرض، `sha-*` برای commit و tag نسخه در رویداد tag هستند. `GITHUB_TOKEN` برای ورود به GHCR استفاده می‌شود؛ secret سفارشی در مخزن لازم نیست.

موفقیت workflow یعنی **ایمیج ساخته و منتشر شده** است، نه این‌که سرور شما به‌طور خودکار آن را دریافت و جایگزین کرده باشد. برای استقرار نسخهٔ جدید با Compose تولیدی:

```bash
docker compose -f docker-compose.prod.yml pull app
docker compose -f docker-compose.prod.yml up -d app
docker compose -f docker-compose.prod.yml ps
```

اگر پنل سرور ایمیج را جداگانه مدیریت می‌کند، از همان پنل pull/redeploy نسخهٔ جدید را انجام دهید. برای استقرار قابل بازگشت، به‌جای `latest` می‌توان tag مشخص `sha-*` یا digest ایمیج را در تنظیمات استقرار ثبت کرد. قبل از تغییر schema یا دیتای واقعی، پشتیبان بگیرید.

## مسیرهای پایدار و بکاپ

| محل                                 | کاربرد                     | اگر از دست برود                                                |
| ----------------------------------- | -------------------------- | -------------------------------------------------------------- |
| PostgreSQL موجود                    | مکان‌ها، آیتم‌ها و قیمت‌ها | دادهٔ واقعی منو از دست می‌رود                                  |
| `/app/uploads`                      | تصاویر بارگذاری‌شده در پنل | URLهای `/uploads/...` در دیتابیس به فایل ناموجود اشاره می‌کنند |
| `/root/.aspnet/DataProtection-Keys` | کلیدهای محافظت cookie      | نشست‌های قبلی مدیر پس از تعویض کانتینر نامعتبر می‌شوند         |

Compose دو volume با نام منطقی `uploads` و `protection_keys` تعریف می‌کند. نام واقعی Docker ممکن است پیشوند نام پروژه داشته باشد. از دیتابیس با ابزارهای PostgreSQL مثل `pg_dump` و از volume آپلودها در همان بازهٔ زمانی پشتیبان تهیه کنید. پس از بازیابی، اتصال DB، URL تصاویر و `/health` را بررسی کنید. کلیدهای Data Protection باید محرمانه بمانند؛ در volume فعلی رمزنگاری در حالت سکون توسط برنامه تنظیم نشده است.

## بررسی سلامت و لاگ‌ها

Dockerfile هر ۳۰ ثانیه `curl -fsS http://127.0.0.1/health` را در کانتینر اجرا می‌کند، با timeout پنج‌ثانیه‌ای و مهلت شروع ۳۰ ثانیه. خروجی موفق API `{"status":"ok"}` و HTTP 200 است. Compose تولیدی از health check داخل ایمیج استفاده می‌کند. `GET /health` در هر درخواست SQL نمی‌زند؛ بعد از startup، قطع موقت دیتابیس ممکن است هم‌زمان با health سبز رخ دهد. برای اطمینان از مسیر داده، `GET /api/venues` یا `GET /api/menu/{id}` را نیز تست کنید.

دستورهای کاربردی:

```bash
docker compose -f docker-compose.prod.yml ps
docker compose -f docker-compose.prod.yml logs --tail=200 app
docker compose -f docker-compose.prod.yml exec app curl -fsS http://127.0.0.1/health
docker network inspect <DB_NETWORK>
docker network inspect <NPM_NETWORK>
```

`docker compose config` مقدارهای environment از جمله رمز را در خروجی چاپ می‌کند؛ خروجی کامل آن را در تیکت یا چت عمومی منتشر نکنید. برای بررسی تعداد و نام سرویس‌ها بدون چاپ secret، از `docker compose -f docker-compose.prod.yml config --services` استفاده کنید.

## ارتقا از استقرار قدیمی

نسخه‌های قبلی ممکن بود یک Nginx جداگانه داشته باشند که upstream آن `api:8080` بود. ایمیج فعلی فرانت‌اند و API را در همان فرایند ASP.NET سرو می‌کند. هنگام مهاجرت، وجود لاگ ASP.NET از `app-1` همراه لاگ Nginx از `sera-restaurant-menu` نشان‌دهندهٔ **دو کانتینر متفاوت** است، نه خرابی `app-1`. تغییر Git، کانتینر قدیمیِ در حال اجرا را متوقف نمی‌کند. در پنل یا Compose مربوط به همان استقرار قدیمی، آن را خاموش کنید و مقصد reverse proxy را به سرویس جدید منتقل کنید. پیش از پاک کردن هر volume قدیمی، بررسی کنید آپلودهای واقعی آن کجا ذخیره شده‌اند.

## امنیت عملیاتی و محدودیت‌ها

- HTTPS را در reverse proxy فعال کنید. cookie مدیریتی با `SecurePolicy=SameAsRequest` برای درخواست HTTPS امن علامت‌گذاری می‌شود.
- رمز دیتابیس و رمز ادمین را به‌صورت secret یا فایل `.env` خارج از Git نگه دارید. این دو رمز مستقل‌اند.
- یک رمز ادمین برای همهٔ مکان‌ها وجود دارد؛ نقش، حساب جداگانه، بازیابی رمز و audit log پیاده نشده‌اند.
- rate limit فقط روی endpoint ورود تنظیم شده است. برای سرویس عمومی بزرگ‌تر، محدودسازی و مانیتورینگ در proxy نیز لازم است.
- `/health` فقط پاسخ‌دهی برنامه را نشان می‌دهد. در صورت نیاز به readiness دیتابیس، endpoint و health policy جدا اضافه کنید.
- پاک‌سازی خودکار فایل‌های آپلودی بی‌استفاده، migration نسخه‌دار و بازیابی خودکار seed ناقص در حال حاضر وجود ندارند.
